# tools/ci/gate_shards.txt — DDR-817 CI gate partition.
#
# Format:  <shard>  <make-target>  <secs>
#
# WHY THIS FILE EXISTS, twice over:
#
# 1. SPEED. The single serial `build-and-boot` job ran its gates in 2 h 08 m;
#    the other four CI jobs finish in under 30 s combined, so that one job WAS
#    the critical path. Shared setup (checkout + toolchain + musl + lwip +
#    image) is ~49 s, i.e. ~0.6 % of the job — which is why splitting by gate is
#    nearly free. Six shards: ~24 min each.
#
# 2. COVERAGE, which turned out to matter more. `ci.yml` hand-listed 111 gate
#    steps and NOTHING checked that list against the Makefile. Eight gates were
#    in the Makefile and in no CI run at all:
#      smoke-sha256 smoke-hkdf smoke-lockbox smoke-rng smoke-sigpipe
#      smoke-privacy-netfilter smoke-blkmq smoke-rqstress
#    That includes the gate for every crypto primitive promoted on "two CI
#    greens". Those greens were real, and they carried no information about
#    those features. `make ci-shard-check` is what stops that recurring.
#
# Assignment is longest-processing-time-first over the durations recorded here,
# NOT round-robin: eleven gates sit at 180 s (TIMEOUT_S=180 QEMU_SMP=4, all with
# a FORBIDDEN_SENTINEL, so DDR-785 early exit does not apply to them). Packed
# badly, those alone would make one shard 33 min and cap the matrix.
#
# Durations are measured, from run 30741785980 (main @ b823bb5, green), via the
# .../actions/runs/<id>/jobs endpoint — EXCEPT for the eight gates above, which
# have never run in CI and are therefore recorded at their own TIMEOUT_S, the
# worst case. They are inputs to the packing only; nothing asserts against them
# at runtime. They are recorded so a future re-balance has evidence in the file
# rather than re-deriving it from the API.
