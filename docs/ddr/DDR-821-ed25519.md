# DDR-821 — Ed25519 signatures (RFC 8032)

**Status:** §Design
**Date:** 2026-08-03
**Prerequisite for:** DDR-814 (AGS), DDR-813 (ACC), DDR-815 (signed updates).
**Depends on:** DDR-816 (entropy), and **SHA-512, which does not exist yet**.
**Owner decision:** D-1 — the constant-time gap is accepted on the record.

## §Problem

AGS signs every agent action record so the audit log can be verified **offline
by anyone holding `OWNER_SIGN_PUBKEY`**. That is the whole security property:
the log is only worth something if a holder of the log cannot forge entries in
it. Nothing in `kernel/crypto/` signs anything — the directory holds
`sha256`, `hkdf`, `aead`, `x25519`.

## §Scope named up front, not discovered mid-slice

Ed25519 is specified over **SHA-512**, and this tree has only SHA-256. So this
slice is **SHA-512 and Ed25519**, exactly as DDR-818 was "HMAC *and* HKDF".
Naming it here is what keeps one slice from quietly becoming two.

SHA-512 is not a variant of the SHA-256 code with different numbers. It shares
the Merkle–Damgård shape and differs in every dimension that matters:

| | SHA-256 | SHA-512 |
|---|---|---|
| word | 32-bit | **64-bit** |
| block | 64 B | **128 B** |
| rounds | 64 | **80** |
| round constants | 64 × 32-bit | **80 × 64-bit** (different values) |
| σ/Σ rotations | 7/18/3, 17/19/10, 2/13/22, 6/11/25 | **1/8/7, 19/61/6, 28/34/39, 14/18/41** |
| length field | 64-bit | **128-bit** |

It is written as its own file (`sha512.{c,h}`), not as a parameterised
`sha2.c`. Sharing the code would mean templating over word width, rotation
counts and constant tables — more places to be wrong, in the one primitive whose
wrongness is silent, for no benefit either implementation gets.

## §Design

`kernel/crypto/sha512.{c,h}` and `kernel/crypto/ed25519.{c,h}`. Pure C, no
stdlib, no allocation, no hardware acceleration (ADR-034: same source builds for
x86_64/aarch64/riscv64).

```c
/* Deterministic per RFC 8032 — no RNG at signing time. That is a property of
 * Ed25519, not a shortcut: the nonce is SHA-512(prefix || message), so a
 * broken RNG cannot leak the key the way it does in ECDSA. */
void ed25519_sign(uint8_t sig[64], const void *msg, uint32_t msglen,
                  const uint8_t privkey[64]);   /* seed(32) || pubkey(32) */

/* 0 == valid. Any other value == rejected. */
int  ed25519_verify(const uint8_t sig[64], const void *msg, uint32_t msglen,
                    const uint8_t pubkey[32]);

/* pubkey = A = [s]B, where s is derived from the 32-byte seed. */
void ed25519_pubkey(uint8_t pubkey[32], const uint8_t seed[32]);
```

### Curve arithmetic — reuses DDR-820's field, not its group

Ed25519 is a twisted Edwards curve over **the same field** `p = 2^255 - 19` that
DDR-820 already implements. The field layer (5×51 limbs, `fe_mul`, `fe_sq`,
`fe_invert`, `fe_cswap`) is reused; **the group law is not** — Montgomery
`x`-only ladder and Edwards extended coordinates are different arithmetic.

This means DDR-820's field code becomes shared, which has a consequence worth
stating: **a field bug now breaks both primitives**, and its blast radius grows
from key agreement to signing. That cuts both ways and is on balance good — the
field is the most-tested part of DDR-820 (7 RFC vectors including a
constant-independent commutativity check) and duplicating it would create a
second, less-tested copy.

**Concrete refactor:** `x25519.c`'s field helpers move to
`kernel/crypto/fe25519.{c,h}`; `x25519.c` and `ed25519.c` both include it.
`smoke-x25519` must stay green across that move — it is the regression test for
the refactor, which is a reason to **not start this until `smoke-x25519`
passes.** See §Sequencing.

Also needed and new: scalar arithmetic mod `L = 2^252 + 27742317777372353535851937790883648493` for the
`S = r + H(R,A,M)·s` step. Separate modulus, separate reduction, own file
section.

### The honest part, same as DDR-820 §The honest part first

**Constant-time by construction, unverifiable by any gate here.** No branch and
no memory index depends on a secret. Signing must not leak `s` or the nonce `r`
— a leaked nonce recovers the private key from a single signature, which is
strictly worse than X25519's exposure.

`ed25519_verify` handles only public data and does not need to be constant-time;
that is stated so nobody "hardens" it and slows verification for no reason.

**QEMU under TCG cannot observe timing.** `smoke-ed25519` green means the
vectors pass and the A/B discriminates — nothing about side channels.
Production use requires review with an instrument that can measure it.

## §Test vectors — RFC 8032 §7.1

| # | vector | why this one |
|---|---|---|
| 1 | TEST 1 — **empty message** | the length-0 path, which no other vector reaches and which is easy to get wrong in the SHA-512 padding |
| 2 | TEST 2 — 1-byte message | the ordinary short path |
| 3 | TEST 3 — 2-byte message | a second independent key/message pair |
| 4 | TEST 1024 — 1023-byte message | the **only** vector that forces SHA-512 past one block *and* exercises a message longer than the hash block; a 1-block-only implementation passes 1–3 |
| 5 | **bit-flipped signature must be REJECTED** | the property the primitive exists for. Not in the RFC as a case; expected result is "rejected" |
| 6 | **wrong-pubkey verify must be REJECTED** | catches a `verify` that checks the signature's self-consistency but never binds it to `A` |
| 7 | SHA-512 alone vs FIPS 180-4 `abc` and the 1M-`a` vector | isolates the hash from the curve — a failure here is unambiguous, and the 1M-`a` case forces the streaming/carry path exactly as it did in DDR-811 |

Vectors 5 and 6 are the load-bearing pair. An `ed25519_verify` that returns 0
unconditionally passes 1–4 completely.

**Provenance caveat, unchanged from DDR-811/818/819/820:** these constants are
**recalled, not fetched**. Unlike X25519 there is no commutativity identity to
fall back on — signature verification has no self-checking algebraic property
that is independent of the published constants. So this slice adds a check the
others did not need: **sign-then-verify round-trip on random messages**, which
depends on no published constant and proves the two halves agree with each
other. It cannot catch "both halves wrong the same way", and that limitation is
stated rather than papered over — vectors 1–4 are what catch that, and they are
why the recalled constants still have to be right.

## §Blast radius

New files, plus the `fe25519` extraction from `x25519.c`. `ed25519.o` and
`sha512.o` are **not** in the kernel link until DDR-814 is their first caller —
the DDR-811/818/819/820 precedent.

`MAX_SYSCALLS` is now 128 (raised from 80 in the DDR-823 audit), so AGS's
NSI 79/80 will register. Before that fix, `SYS_GOAL_VERIFY` at 80 would have
been **silently discarded** and surfaced here as an Ed25519 verification bug.

## §Gate — `smoke-ed25519`

Opt-in via `QEMU_PROBES=ed25519`. Sentinel `PRADYOS_ED25519_VECTORS_OK`;
`FORBIDDEN_SENTINEL: PRADYOS_ED25519_STUB`, `ED25519 FAIL`.

Registered in `tools/ci/gate_shards.txt` in the same commit — `ci-shard-check`
fails otherwise, which is the DDR-817 lesson.
`ci-start-align-check` covers the probe's `_start` (DDR-823).

* **A** — `ed25519.o` unlinked → **artefact cannot be built.** Verified by the
  *link* failing, not by the probe printing nothing: `ld -nostdlib` resolves
  undefined symbols to 0, which is the DDR-811 arm-A trap that was vacuous three
  times.
* **B** — SHA-512 round count 80→64 → vector 7 fails and all signatures are
  wrong → **FAIL**. Isolates the hash from the curve.
* **C** — `ed25519_verify` returns 0 unconditionally → **vectors 1–4 still
  PASS**, 5 and 6 FAIL. Proves the rejection vectors are load-bearing rather
  than decorative.
* **D** — correct → **PASS**.

Three distinct kernel SHAs across B/C/D. A shared SHA is the DDR-791 trap and
invalidates the run — and per DDR-822, confirm the probe ELF's mtime moved too,
because that trap was live in the Makefile until this session.

## §Sequencing — do not start before this is true

`smoke-x25519` must be **green on a clean host** first. This slice refactors
`x25519.c`'s field layer into a shared file, and `smoke-x25519` is the only
regression test for that refactor. Refactoring against a gate that does not
currently pass means a later failure cannot be attributed.

## §Explicitly not asserted

Constant-time execution, in signing or key derivation. See §The honest part.

## §Implementation — SHA-512 half done

`kernel/crypto/sha512.{c,h}` written and **verified against FIPS 180-4 on the
host**:

```
empty                  OK
abc                    OK
2-block (896-bit)      OK
1M 'a' streamed        OK
```

The 1M-`a` case is fed in **1000-byte chunks** (1000 = 7×128 + 104), not
128-byte ones. A block-aligned chunk size never exercises the partial-block
carry in `sha512_update`, so it would pass against a broken carry — the exact
defect DDR-811 shipped three vacuous arms over before it was caught. Chunk size
is chosen by which code path it reaches, not by convenience.

Two details worth recording because both produce plausible wrong digests:

1. **The 128-bit length field.** FIPS 180-4 specifies 128 bits; carrying only 64
   would wrap silently past 2^64 bytes. Unreachable in practice, one compare to
   get right, and wrong-loudly beats wrong-silently.
2. **Length captured before padding.** `sha512_final` reads the bit count *then*
   pads, because `sha512_update` advances the counter. Reversing those two lines
   compiles and produces a confident wrong digest for every input.

Ed25519 itself is not yet written — it is gated on `smoke-x25519` going green,
per §Sequencing, because this slice refactors the shared field layer and that
gate is the only regression test for the refactor.
