# DDR-1052 — Keccak-f[1600] / SHA-3 / SHAKE (FIPS 202): the PQC prerequisite

**Status:** IMPLEMENTED + gated + M1/M2/M3 mutation-proven.
**Scope:** step 1 of Post-Quantum Security, which is **mandatory v1 scope**
(operator, PR #17 Part B) and lands **before** the ISO.
**Shipped kernel:** `15e140e21c2d8270`, 1,192,330 B, `-Werror` clean.

---

## 1. Why this is step 1 and not an extra

`docs/PRE_LAUNCH_CHECKLIST.md` §5.1b.1 fact 1: there is **no SHA-3 anywhere in
the tree** — `kernel/crypto/` held SHA-256, SHA-512, X25519, Ed25519, HKDF and
AEAD, and zero Keccak. **Both** ML-KEM (FIPS 203) and ML-DSA (FIPS 204) are built
on SHAKE128/256 for matrix expansion, coefficient sampling and hashing. So a
Keccak core is a **prerequisite**, and the build order is fixed:
Keccak/SHAKE → KAT acquisition → ML-DSA → application.

Size is not the constraint: `kernel.bin` went 1,175,946 → **1,192,330 B**
against the 1,572,864 B gate (+16,384 B for the core and the probe ELF), leaving
380,534 B.

## 2. THE CONSTRAINT THAT SHAPED EVERYTHING: known-answer, not round-trip

§5.1b.1 fact 4 is the load-bearing one, and it applies to a hash exactly as it
does to a signature. **A gate that hashes something and checks the result
against its own output proves nothing** — any self-consistent wrong
implementation passes, including one that is not Keccak at all. That is the
dead-arm class this project has recorded nine times.

So every expected value is **generated by an implementation that is not this
one**: Python's `hashlib` SHA-3/SHAKE, pinned byte-exact into
`kernel/crypto/keccak_kat.h`. And `hashlib` itself is not merely trusted — the
empty-input digests it produced were cross-checked against the **published FIPS
202 constants** (`SHAKE128("")` begins `7F9C2BA4`, `SHAKE256("")` `46B9DD2B`,
`SHA3-256("")` `A7FFC6F8`), so the chain terminates in public knowledge rather
than in one library.

### 2.1 The constants are derived and proved, not transcribed

The 24 round constants and the rho offsets were generated from the FIPS 202
definitions, and then the whole permutation was **re-implemented in Python and
checked against `hashlib`** across four functions and four message lengths
before a line of C was written.

That was not ceremony: **the first generator produced `RC[0] = 0x03` instead of
`0x01`** — a wrong LFSR index. Transcribing 24 magic 64-bit constants by hand is
exactly where a silent, total break comes from, and this caught one.

## 3. Vector selection — why these lengths

| # | vector | what it catches |
|---|---|---|
| 1-6 | SHAKE128/256, SHA3-256/512 of `""` and `"abc"` | gross breakage only |
| **7-9** | **SHAKE128 of 167 / 168 / 169 bytes** | **absorb rate boundary** (rate 168) |
| **10-12** | **SHAKE256 of 135 / 136 / 137 bytes** | **absorb rate boundary** (rate 136) |
| **13-14** | SHAKE128/256 squeezed to 200 bytes, **tail** asserted | squeeze past the rate |
| 15 | same message in 1/7/160/1-byte chunks | streaming offset across `update()` calls |

Vectors 1-6 are the standard smoke values and catch almost nothing. The
boundaries are where `pad10*1` and multi-block absorb go wrong. Vector 15 is not
a KAT — it is a consistency arm, and it exists because a one-shot-only vector
set **never calls `update()` twice** and so cannot see a broken streaming offset.

## 4. Implementation notes

- **Endian-neutral by construction.** Bytes are XORed into and read out of the
  lane array with explicit shifts, never by aliasing the state as bytes, so the
  FIPS 202 little-endian lane convention holds regardless of host byte order.
  No `#ifdef`, no `bswap`. Same reasoning `sha256.h` gives for staying pure C:
  one object builds for x86_64, aarch64 and riscv64, and an ISA-specific path
  would pass its gate on one and fail at runtime on the others.
- **Lane index == byte_offset / 8.** With the flat `st[25]` and FIPS 202's
  ordering, `x + 5y` *is* the byte offset divided by 8, so absorb and squeeze
  index the array directly with no mapping table.
- **The pad's two XORs are into one position when `pos == rate-1`.** The domain
  byte and the `0x80` collide in that case; they are two XORs rather than two
  writes precisely so the collision is harmless. **M2 below is that exact bug.**

## 5. Mutation proof — three mutants, three different arms

Run first on the host (`cc -Werror`, the same source), then M2 re-applied to the
**shipped kernel** so the *gate* is proven, not just the code.

| | mutation | first failing vector | why it matters |
|---|---|---|---|
| **M1** | one round constant, `RC[23]` low bit | **1** | caught immediately |
| **M2** | skip the `0x80` when it collides with the domain byte | **7** | **passes vectors 1-6** — a real pad bug that every empty/`"abc"` vector misses |
| **M3** | no permutation on a squeeze past the rate | **13** | the multi-block squeeze arm |

**M2 is the one that justifies the vector set.** It is a plausible
implementation bug, it fires only when `len % rate == rate-1`, and an
implementation carrying it passes every standard smoke vector. Without vectors
7-12 it would have shipped.

**M2 against the gate**, kernel `b0d86bfc4d5c97f2`: `make smoke-shake` → **rc=2**,
capture carrying `PRADYOS_SHAKE_STUB first_bad_vector=7`. Reverting returns
`15e140e21c2d8270` **bit-for-bit**.

## 6. The gate is verified non-vacuous

`rc=0` alone would be worthless — DDR-1041 recorded three gates whose `rc=0`
proved nothing because their marker was in another file. So the capture was read
back directly: `PRADYOS_SHAKE_VECTORS_OK n=15` is present **1** time, preceded by
`[fwcfg] probes="shake"` and `[user] ELF loaded (embedded); FIPS 202 SHAKE vector
probe spawned`. The probe really ran, in ring 3, in the shipped kernel.

`user/shaketest.c` **links `kernel/crypto/keccak.c`** — the same source the
kernel builds, compiled a second time for ring 3, exactly as `sha256test.c` does.
A separate userspace copy could drift from the kernel's while the gate stayed
green.

## 6.1 Regression suite

Shipped kernel `15e140e21c2d8270`, hash recorded before and after so the gates
provably ran the binary being shipped:

smoke-sha256 rc=0    smoke-blkmq     rc=0

`hygiene_check.sh` ALL SIX, including `ci-probe-rodata-check` on the new probe —
DDR-1032 found a probe whose `static const char *argv[]` landed in writable data,
so a new ring-3 probe is exactly what that check exists for. `ci-shard-check`
measures **174** gates.

## 7. What this does NOT do

- **It is not ML-DSA or ML-KEM.** It is their prerequisite. No signature or KEM
  exists yet, and nothing in this change is post-quantum by itself.
- **No consumer yet.** Nothing calls SHAKE in anger — the audit ledger still uses
  SHA-256 (DDR-812/F#76). Wiring ML-DSA into it is the application step.
- **Not constant-time-audited.** Keccak has no data-dependent branches or table
  lookups by construction, which is why it is a reasonable starting point, but
  no timing measurement was taken and none is claimed.
- **The next step's risk is named:** ML-DSA KATs cannot come from `hashlib` —
  Python has no ML-DSA. §5.1b.1 fact 3 measured the only route
  (`raw.githubusercontent.com`; `csrc.nist.gov` is blocked by the proxy). If
  pinned FIPS 204 vectors cannot be obtained, the honest output is a
  DDR-1038-shaped blocker naming that — **not** an unverified implementation
  with a sign/verify round-trip gate.
