# DDR-820 — X25519 key agreement (RFC 7748)

**Status:** §Design
**Date:** 2026-08-02
**Prerequisite for:** DDR-813 (ACC's ephemeral key agreement).
**Depends on:** DDR-816 (private scalars need entropy).
**Sequenced by:** DDR-813 §Blocker 4 — 818 ✅ → 819 ✅ → **820** → 821 → 813.

## §Problem

ACC agrees a shared secret between the kernel and a peer, feeds it to
DDR-818's HKDF to derive `K_session` and `K_owner`, and encrypts with DDR-819's
AEAD. The agreement itself does not exist: the only `x25519` matches anywhere in
`kernel/` are prose in comments this project wrote.

## §The honest part first

Every primitive before this one is validated by vectors that *fully* determine
correctness: a wrong SHA-256, HKDF or Poly1305 produces wrong bytes, and the
gate compares bytes.

**X25519 is different, and the owner has accepted it on the record (D-1).** The
security property that matters here is not only "computes the right point" but
"takes the same time and touches the same memory regardless of the secret
scalar". An implementation can pass every RFC 7748 vector *perfectly* and still
leak the private key through timing or cache behaviour — and a leaked private
key is the whole of ACC's, AGS's and fleet update's security.

**No gate this project can run detects that.** QEMU under TCG does not model
cache or pipeline timing, and even on real hardware a black-box boot gate is the
wrong instrument. So:

- The implementation is **constant-time by construction**: no branch and no
  memory index depends on a secret bit. Where the ladder needs a conditional
  swap it uses an arithmetic mask, not an `if`.
- The gate asserts **correctness only**, and this DDR states plainly that it
  does not assert constant-time.
- **Production use requires side-channel review** by an instrument that can
  actually measure it (`dudect`, `ctgrind`, or a formally verified
  implementation such as fiat-crypto). Recorded here so the gap travels with the
  code rather than living only in a session transcript.

This is the same class of gap as DDR-819's tag comparison, one order larger.

## §Design

`kernel/crypto/x25519.{c,h}`. Pure C, no stdlib, no allocation, no hardware
acceleration — the same source must build for x86_64, aarch64 and riscv64
(ADR-034).

```c
/* out = scalar * point. Returns 0, or <0 if the result is all-zero (a
 * small-order input point — a contributory-behaviour check, not decoration:
 * an all-zero shared secret means the peer chose it, not agreed it). */
int x25519_scalarmult(uint8_t out[32], const uint8_t scalar[32],
                      const uint8_t point[32]);

/* out = scalar * basepoint (u = 9). The public-key half. */
int x25519_scalarmult_base(uint8_t out[32], const uint8_t scalar[32]);
```

### Field representation — decided, not inherited

**5 limbs of 51 bits over `uint64_t`, with `unsigned __int128` products.**

The alternative is the classic 10-limb 25.5-bit `ref10` layout over 32-bit
words, whose merit is not needing `__int128`. That merit does not apply here:
all three ADR-034 target ISAs are 64-bit, and clang provides `__int128` on all
of them. `__int128` is not currently used anywhere in `kernel/`, so this
introduces the dependency — stated explicitly rather than discovered later. If a
32-bit target is ever added, this file needs the 10-limb layout; that is the
cost, and it is recorded.

Chosen because the 5×51 code is materially shorter and has fewer carry chains,
and carry propagation is where a hand-written field implementation is most
likely to be subtly wrong in a way short vectors do not catch.

### The ladder

Montgomery ladder over Curve25519 (`p = 2^255 - 19`, `A = 486662`), the standard
RFC 7748 §5 formulation, processing the scalar from bit 254 down to 0 with a
`cswap` on each step.

`cswap` is the constant-time hinge and is written as:

```c
static void fe_cswap(fe a, fe b, uint64_t swap) {
    uint64_t m = 0 - swap;              /* 0 or all-ones; no branch */
    for (unsigned i = 0; i < 5; i++) {
        uint64_t t = m & (a[i] ^ b[i]);
        a[i] ^= t; b[i] ^= t;
    }
}
```

An `if (swap)` here would be correct and would pass every vector.

Scalar clamping per RFC 7748 §5: clear bits 0–2 of byte 0, clear bit 7 and set
bit 6 of byte 31. Clamping is what forces the scalar into the right cofactor
class and fixes the leading bit so the ladder's length does not depend on the
secret.

The `u`-coordinate's high bit is masked on input, per §5 ("implementations MUST
mask the most significant bit").

## §Test vectors — RFC 7748

| # | vector | why this one |
|---|---|---|
| 1 | §5.2 scalarmult, first case | the ordinary path |
| 2 | §5.2 scalarmult, second case | a second independent point/scalar pair; a single vector can be matched by a broken implementation with a lucky carry |
| 3 | §6.1 Alice pub = `a·G`, Bob pub = `b·G` | exercises `scalarmult_base` specifically, which vectors 1–2 never reach |
| 4 | §6.1 **`a·(b·G) == b·(a·G)`** | the property the primitive exists for. It is the only check that would survive if all the published constants in this file were wrong together |
| 5 | all-zero output rejection: `scalarmult` on a small-order point | asserts the contributory check actually fires, rather than being unreachable code |

Vector 4 is the load-bearing one for a reason worth stating: constants in this
file are **recalled, not fetched** — the same caveat as DDR-811/818/819. Vectors
1–3 compare against recalled bytes, so a wrong constant fails loudly (good) but
a *consistently* wrong set could in principle agree with a wrong implementation.
Vector 4 compares the implementation against **itself under the commutativity
that Diffie-Hellman requires**, and depends on no published constant at all. It
is the check that cannot be fooled by bad provenance.

## §Blast radius

New files only. `x25519.o` is **not** in the kernel link until DDR-813 is its
first caller — the DDR-811/818/819 precedent, and the reason `nm` shows no new
undefined symbols in `kernel.elf` after this slice. The probe compiles the same
source a second time with the user code model.

## §Gate — `smoke-x25519`

Opt-in via `QEMU_PROBES=x25519`. `FORBIDDEN_SENTINEL: PRADYOS_X25519_STUB`.
Sentinel on success: `PRADYOS_X25519_VECTORS_OK`.

Registered in `tools/ci/gate_shards.txt` in the same commit — DDR-817 found
eight gates that existed and had never run in CI, and `make ci-shard-check` now
fails if a gate is not in a shard. A new gate that is not registered is a gate
that does not run.

* **A** — `x25519.o` unlinked from the probe → **artefact cannot be built**.
  Note the DDR-811 trap: `ld -nostdlib` resolves undefined symbols to 0 rather
  than erroring, so this arm must be verified by the *link failing*, not by the
  probe running and printing nothing.
* **B** — `fe_cswap` replaced with an unconditional swap → wrong result for
  every scalar → **FAIL** on vectors 1–4.
* **C** — `scalarmult_base` given basepoint `u = 1` instead of `u = 9` →
  **vectors 1 and 2 still PASS** (they supply their own point) while 3 and 4
  fail. Isolates the base-point constant from the ladder, and proves vector 3 is
  load-bearing rather than a duplicate of 1–2.
* **D** — correct → **PASS**.

Three distinct kernel SHAs required across B, C, D (arm A builds nothing). A
shared SHA is the DDR-791 stale-artefact trap and invalidates the run.

## §Explicitly not asserted

Constant-time execution. See §The honest part first. `smoke-x25519` green means
*the vectors pass and the A/B discriminates*, and nothing about timing-channel
resistance.

### Defect 1 — the ladder constant, and vector 4 doing exactly its job

The first version paired `a24 = 121665` with the `BB` form of the ladder step.
Every constant-comparing vector failed **and the commutativity check PASSED.**

That combination is diagnostic and it is why vector 4 was specified. A
consistent group law with a wrong parameter still commutes; broken field
arithmetic does not. So the failure pattern said "one constant is wrong",
not "the 250 lines of field arithmetic are wrong", and it narrowed the search
to a single line without any bisection.

Deriving rather than recalling settles it:
`Z₂ = 4XZ((X−Z)² + ((A+2)/4)·4XZ)` with `4XZ = AA − BB = E`, so the `BB` form
needs `(A+2)/4 = 121666`. RFC 7748 §5 writes the algebraically identical
`E·(AA + 121665·E)` with `a24 = (A−2)/4 = 121665`. **Both constants are correct
— for different forms of the same expression.** Mixing them is off by exactly
`E`. The comment on `fe_mul121666` now says so, because this is a trap that
looks like a typo and is not.

### Defect 2 — `_start` stack alignment, which is not a crypto bug at all

The in-QEMU probe first died on
`[trap] user #GP pid=29 rip=0x80000020FD`, at
`movaps %xmm0,-0x20(%rbp)`.

SysV enters a process at `_start` with **RSP 16-byte aligned** (pointing at
argc), and `kernel/exec/elf.c:215` does exactly that — the kernel is correct.
But a compiler treats `_start` as an ordinary function, entered via `call` with
RSP ≡ 8 (mod 16). So `_start`'s frame is off by 8, every callee inherits it, and
the first 16-byte-aligned stack access faults. `movaps` on a misaligned address
raises **#GP**, not #AC, which is why it reads like a protection bug.

This is why a real libc `_start` is assembly. Fixed with
`__attribute__((force_align_arg_pointer))`.

**Every freestanding probe in `user/` has this latent hazard.** The others
survive only because their generated code never emitted an aligned SSE stack
access; nothing about them is safe by design. Worth a separate slice.

### Open — the gate still does not reach its sentinel

After the alignment fix the probe no longer traps, and it also produces no
output within 90 s. It is not slow: the same source runs the same seven checks
in **3 ms at -O0 on the host**, so even a 1000× TCG penalty is seconds. The
probe is therefore hung or dying silently, and the cause is **not yet known** —
recorded as unknown rather than guessed at.

**Confirmed, not inferred:** re-run at `TIMEOUT_S=300` — more than 3x the gate
window — the sentinel still never appears and the probe still never traps. So
"slow under TCG" is eliminated as a hypothesis by measurement rather than by the
3 ms host argument alone. It is stuck or dead, not late.

Not yet ruled out: the large-code-model `.ltext`/`.lrodata` orphan sections
(`user.ld` names neither, and lld's orphan placement is what currently puts them
in the PT_LOAD); stack depth in `fe_invert`'s addition chain; or `sched_create`
leaving a field uninitialised for this thread shape.

`smoke-x25519` is consequently **excluded from the CI shard matrix, explicitly
and with that reason recorded in `tools/ci/shard_check.sh`.** A gate failing for
an unknown reason must not be silently absent — which is the DDR-817 finding —
and must not be red for everyone either. It is re-registered the moment it
passes, and DDR-813 must not consume this primitive until then.

**What this primitive currently rests on:** RFC 7748 vectors under `gcc` on the
host, including a commutativity check that depends on no published constant.
That is real evidence and it is not the same as a green gate.
