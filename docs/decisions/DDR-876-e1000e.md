= DDR-876 — Intel e1000e NIC driver (Group 4 item 25)

**Status:** Accepted
**Date:** 2026-08-09
**Scope:** `kernel/drivers/net/e1000e.{c,h}`, `kernel/drivers/net/netbuf.c`,
`kernel/main.c`, `boot_test.sh`, `smoke-e1000e`.

## Scope, stated before the detail

An 82574L (`8086:10D3`, QEMU's `e1000e`) driver with RX and TX descriptor rings,
the MAC read from the Receive Address registers, and a polled receive path —
behind the same five-function API as `virtio_net.h`, so the lwIP bridge above
sees one interface regardless of which NIC the platform has.

**Not implemented:** MSI-X interrupts, checksum/TSO offload, multiple queues,
VLAN filtering, EEPROM access, PHY link renegotiation. Each is a real e1000e
feature; none is needed by anything in this queue, and each adds a failure mode
that would need its own gate.

## Why polled and not interrupt-driven

Not a shortcut, and worth stating because "polled" usually is one.

This kernel's INTx path is shared and chained (`idt.c`), and virtio-net already
owns MSI-X vector 54. A second NIC on a shared line means both drivers' handlers
run for every assertion from either, and the failure mode when that is wrong is a
*lost* interrupt — a network that works until it silently stops. Polling from a
bounded loop has no shared-line semantics to get wrong.

Moving to MSI-X is a contained change: `pcie_msix_setup()` already exists and the
vector plumbing is device-agnostic.

## The things that make e1000e subtly wrong

**1. The tail pointer is "one past the last buffer you own."** Arming RDT equal
to RDH tells the NIC it owns *nothing* and receive silently stops — no error, no
interrupt, just a NIC that never receives. RDT is armed at `NRX - 1`, and after
consuming a descriptor it advances to the descriptor just released, never to
head.

**2. RDLEN/TDLEN are in BYTES, not entries.** A length in entries yields a ring
16× too small; the NIC wraps early and overwrites descriptors the driver still
believes are pending. Both rings come from whole PMM pages, which also satisfies
the 16-byte base alignment by construction.

**3. STATUS.DD is the only valid "is this mine" test.** Reading a descriptor's
length before DD is set reads whatever the ring held previously — usually a
plausible-looking length from an earlier packet.

**4. The BAR is not one page.** The register file reaches RAH0 at 0x5404, so a
single-page mapping page-faults on the very first MAC read. It did, on the first
run: `#PF CR2=0xFEB85400`. The size is now *probed* (write-all-ones, read back,
restore) rather than assumed, and rejected if implausible — assuming a size is
what produced the fault, so replacing one assumed constant with another would
have been the same mistake with a bigger number.

**5. Bus-master enable.** Without it the NIC cannot DMA, both rings stay empty,
and the device looks like a dead link rather than an unconfigured one.

The PCI match is on **vendor AND device** (`0x8086`/`0x10D3`), not class 0x02.
Class 0x02 is every Ethernet controller; this driver programs 82574L registers
and would misdrive anything else that merely claims to be a NIC. Same lesson as
DDR-875's class-plus-subclass match for AHCI.

## The netbuf pool is shared, and had to be budgeted

`netbuf` is a fixed pool sized for one NIC (40 buffers). e1000e's rings pinned
enough of it that init failed with "netbuf exhausted". Fixed on both sides: the
rings are 16 RX / 8 TX (kept a multiple of 8 so RDLEN stays a multiple of 128
bytes), and `NETBUF_COUNT` is raised to 72 with the second NIC's rings written
into the comment as part of the budget. A second consumer of a fixed pool has to
appear in that pool's arithmetic or it fails at the worst possible time.

## The gate proves a round trip, not a probe

`smoke-e1000e` attaches a real `-device e1000e` (opt-in via `QEMU_E1000E`, for
DDR-875's reason: an always-on device changes PCI enumeration for every gate).
Bring-up sends a broadcast ARP request and polls for slirp's reply, and the gate
requires all three of:

```
[e1000e] up, mac=52:54:00:
[e1000e] TX OK
[e1000e] RX OK n=
```

The MAC prefix proves RAL0/RAH0 returned real register data rather than zeros.
`RX OK` is the assertion that carries the weight: one ARP round trip is the only
thing that exercises the TX descriptor, the RX descriptor, the DD bit and the
tail pointer together. All four can be wrong while the device still probes and
prints cleanly.

The self-test is also why `e1000e_poll()` is not a function nothing calls.

## Mutation matrix — 3 of 4 killed, and the survivor named

| Mutation | Gate |
|---|---|
| M1 `RDT = 0` (own no buffers) | **killed** — no `RX OK` |
| M2 `RDLEN` in entries not bytes | **killed** — no `RX OK` |
| M3 test `d->length` instead of `STATUS.DD` | **SURVIVED** |
| M4 drop bus-master enable | **killed** — no `RX OK` |
| RAL0 offset 0x5400 → 0x5408 | **killed** — MAC pattern absent |

**M3 survives and the code is still correct.** The rings are zeroed at init and
QEMU writes length and status together, so with a single packet `length != 0`
and `DD` are indistinguishable. The defect it models — reading a stale length
from a reused descriptor — needs ring wraparound to appear, which one ARP reply
cannot produce. Stated rather than papered over: the DD check is right on the
Intel SDM's terms, but **this gate does not prove it**. A multi-packet RX gate
that wraps the ring would kill M3, and is the natural next step if this driver
ever carries real traffic.

## What is proven, and what is not

**Proven:** PCI probe → BAR sizing → multi-page MMIO map → interrupt mask →
link-up → MAC from RAL/RAH → ring allocation → TX descriptor → RX descriptor and
tail advance, end to end against slirp.

**Not proven:** ring wraparound (see M3), sustained throughput, link-state change
handling, and the lwIP bridge running *over* e1000e — the bridge is still bound
to virtio-net, and switching it is a separate change with its own gate.

Gates green: `smoke-e1000e`, `smoke`, `smoke-fs`, `smoke-fs-rw`,
`smoke-fs-sfs-rw`, `smoke-fs-ext4`, `smoke-user`. Zero warnings under `-Werror`.
138 gates across 6 shards.

**Group 4 item 25 complete.**
